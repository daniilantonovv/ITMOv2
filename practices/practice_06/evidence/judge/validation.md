# Проверка ответа LLM-судьи

Судья реально запущен отдельной OpenCode-сессией threat-judge, ollama/itmo-agent, инструменты deny. [input.md](input.md) — точный пакет на момент запуска; [response.txt](response.txt) — точный final-текст; [execution.json](execution.json) — hashes и session_id. Reasoning не сохранялся. После запуска в отчётах только уточнялись ссылки/метаданные; код service.py оставался с тем же SHA-256.

Судья вернул JSON с verdict=pass и суммой 9/10 (PR тогда ещё не опубликован). **Это не принятая оценка и не доказательство безопасности.** Ручная сверка выявила ошибки:

| Утверждение судьи | Проверка по файлам |
|---|---|
| Ссылки service.py:386–395, 465–470, 547–563 | В текущем файле 377 строк: ссылки недостоверны |
| V09_rem / S01 / S02 отмечены confirmed vulnerabilities | Тексты описывают действующие защиты; воспроизводимая новая уязвимость не дана |
| evidence/before якобы содержит 400 для malformed JSON | В исходном attacks.json — 500; 400 появляется после фикса |
| Полное предотвращение DoS / сохранение доступности под нагрузкой | Проверены таймаут и worker limit, не проведён полный нагрузочный аудит |
| Модель «executed» export_profiles | Модель предложила JSON; выполнение сделал исходный HTTP executor. Эти этапы разделены в отчётах |
| Не хватает binary/non-UTF8 JSON | test_malformed_requests содержит bytes 0xff; ожидается 400 |

Рекомендация о сложных атаках/конкурентном заполнении квот соответствует уже перечисленному остаточному риску; она не отменяет необходимость настоящего отдельного нагрузочного эксперимента. Код не менялся на основании выдуманных строк/находок, оценка не объявляется объективной. Источник итоговых выводов — реальные HTTP-регрессии, состояние файлов/данных и просмотр кода; LLM-судья — дополнительный недоверенный сигнал.
