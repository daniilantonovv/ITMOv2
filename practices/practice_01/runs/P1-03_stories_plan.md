# P1-03 — продуктовые артефакты по Master Prompt v1 (OpenCode, vsellm/openai/gpt-5, agent plan)

Запрос — `P1_03_task.md` (текст в [`../prompts.md`](../prompts.md#p1-03-запрос)), вложение `MASTER_PROMPT_v1.md`. Ответ без правок.

**User Stories**
- Как инженер-ревьюер, я хочу отправить diff PR в POST /api/reviews и получить структурированный ответ с summary, risks (не более 3) и checks, чтобы быстро понять ключевые риски и что проверить.
- Как владелец безопасности, я хочу, чтобы перед вызовом внешнего LLM из diff удалялись токены, пароли и приватные ключи, чтобы исключить утечку секретов (SEC-1).
- Как владелец платформы, я хочу, чтобы при длине diff более 20 000 символов запрос отклонялся с HTTP 413, чтобы защитить сервис от слишком больших входов (API-1).
- Как SRE, я хочу, чтобы таймаут внешнего LLM-вызова был 10 секунд и ошибка превращалась в контролируемый ответ, чтобы сервис стабильно отвечал даже при деградации внешней зависимости (REL-1).

**Acceptance Criteria (Gherkin)**
```gherkin
Feature: POST /api/reviews — AI-помощник ревьюера PR

  # Позитивный сценарий
  Scenario: Успешная проверка валидного diff
    Given валидный diff длиной менее 20 000 символов без сетевых ошибок
    When я отправляю POST /api/reviews с этим diff
    Then я получаю ответ, в котором summary — строка
      And risks — массив из 0..3 элементов
      And у каждого риска есть поля file, line, evidence, risk
      And checks — массив строк
      And лог запроса содержит только request_id, длительность и статус (без diff и ответа модели)  # OBS-1

  # Негативный сценарий
  Scenario: Слишком длинный diff отклоняется
    Given diff длиной более 20 000 символов
    When я отправляю POST /api/reviews с этим diff
    Then я получаю HTTP 413  # API-1
      And тело ответа не раскрывает содержимое diff

  # Граничный сценарий по длине
  Scenario: Ровно 20 000 символов допускается
    Given diff длиной ровно 20 000 символов
    When я отправляю POST /api/reviews с этим diff
    Then запрос принимается (не 413)  # API-1
      And вызывается внешний LLM после удаления секретов из diff  # SEC-1

  # Позитивный сценарий безопасности
  Scenario: Секреты редактируются перед LLM
    Given diff содержит значения вида "token=abcd1234" и "PRIVATE_KEY=-----BEGIN"
    When вызывается внешний LLM
    Then в переданном prompt вместо секретов присутствует [REDACTED]  # SEC-1

  # Негативный/устойчивость
  Scenario: Таймаут внешнего LLM
    Given внешний LLM не отвечает более 10 секунд
    When сервис формирует результат
    Then ошибка таймаута преобразуется в контролируемый ответ  # REL-1
      And ответ соответствует формату: summary, risks (≤3), checks  # OUT-1
      And лог не содержит diff и ответа модели  # OBS-1
```

**План Поставки (Инкременты)**
1. Ограничение размера и каркас API
   Наблюдаемый результат: POST /api/reviews существует; запросы с diff > 20 000 символов возвращают HTTP 413; валидные запросы принимаются.
   Что делает человек: уточняет контракт входа/выхода согласно OUT-1; предоставляет примеры валидных и больших diff.
   Что делает AI/код-агент: создает эндпоинт, валидирует размер входа, возвращает 413 при превышении, заготовка ответа OUT-1.
   Как проверить: отправить payload на 20 001 символ → 413; отправить на 20 000 → не 413.

2. Редакция секретов (SEC-1) и наблюдаемость (OBS-1)
   Наблюдаемый результат: перед внешним LLM все секреты из diff заменяются на [REDACTED]; логи содержат только request_id, длительность и статус.
   Что делает человек: предоставляет набор тестовых строк с токенами/паролями/ключами; описывает примеры, что считать секретом.
   Что делает AI/код-агент: реализует слой редактирования и применение перед LLM-вызовом; настраивает логирование, исключая diff и ответ модели.
   Как проверить: интеграционный тест перехватывает формируемый prompt к LLM и убеждается в наличии [REDACTED]; ревью логов на наличие только разрешенных полей.

3. Интеграция с внешним LLM и таймаут 10 секунд (REL-1)
   Наблюдаемый результат: при ответе LLM до 10 секунд — нормальная обработка; при >10 секунд — контролируемый ответ без ошибок наружу.
   Что делает человек: определяет поведение контролируемого ответа при таймауте (какие summary/risks/checks допустимы).
   Что делает AI/код-агент: добавляет таймаут 10 секунд на LLM-вызов и обработку ошибок; формирует валидный ответ по OUT-1 при таймауте.
   Как проверить: мок LLM с задержкой 11+ секунд → ответ формата OUT-1 без 5xx; мок с задержкой <10 секунд → успешный ответ.

4. Контракт OUT-1 и QA-1-правила на формирование результата
   Наблюдаемый результат: ответ строго следует OUT-1; в risks не более трех элементов; каждый риск подтверждается строкой diff или правилом; SCOPE-1 соблюдается.
   Что делает человек: утверждает правила трансформации ответа модели в OUT-1 и отсечения лишних рисков.
   Что делает AI/код-агент: реализует пост-обработку ответа модели (срез до 3 рисков, проверка наличия evidence и ссылок на правила, формирование checks).
   Как проверить: тестовые дифы с 4+ потенциальными рисками → в ответе максимум 3; риски без evidence не попадают в результат; поля ровно summary/risks/checks.

**Главный Архитектурный Риск и Его Проверка**
- Риск: Недостаточная редакция секретов до вызова внешнего LLM приведет к утечке токенов/паролей/приватных ключей, нарушая SEC-1.
- Как проверить:
  - Набор детерминированных тестов на входные шаблоны секретов (токены, пароли, приватные ключи, вариации кейсов/разделителей); в каждом — в сформированном prompt вместо значений присутствует [REDACTED].
  - Интеграционное проксирование LLM-вызова с инспекцией последнего «перед отправкой» payload на отсутствие сырых секретов.
  - Нагрузочные проверки с смешанными валидными/псевдо-секретами для выявления ложных отрицаний.
  - Регрессия: при изменении правил редактирования прогон полного набора тестов; блокирующий чек на попадание сырых секретов в prompt.
