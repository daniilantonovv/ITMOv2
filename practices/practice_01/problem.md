# Проблема и метрики

## Проблема

- Пользователь: ревьюер backend-команды, который проверяет PR сервиса на Python/FastAPI (вторичный пользователь — автор PR).
- Ситуация: в репозитории есть семь правил (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1, см. [`context.md`](context.md#факты-и-правила)), но ревьюер сверяет с ними каждый diff вручную и по памяти. Команда строит AI-помощника: `POST /api/reviews` принимает diff и возвращает summary, до трёх рисков и проверки.
- Что происходит сейчас: первый PR помощника ([`TRAINING_PR.diff`](TRAINING_PR.diff)) сам нарушает правила, которые должен ловить: diff без редактирования секретов уходит во внешний LLM (`app/review_service.py:14–15`, SEC-1), нет лимита размера (API-1) и timeout (REL-1), ответ — свободный текст `{"comment": ...}` вместо `summary/risks/checks` (OUT-1), `payload["diff"]` без схемы даёт 500 на пустом теле. Zero-shot LLM-ревью этого же PR ([`prompts.md`](prompts.md) P1-01) выдаёт 14 замечаний без правил и с неверными строками — ревьюеру приходится перепроверять всё руками.
- Почему это мешает пользователю или бизнесу: (1) утечка токенов и ключей во внешний LLM — инцидент безопасности; (2) свободный текст без `file:line` и доказательства нельзя быстро проверить, поэтому помощник не экономит время ревьюера; (3) зависший LLM-вызов держит воркер и ломает CI-интеграцию.
- Что не входит в задачу: публикация комментариев в GitHub и любые действия в PR (SCOPE-1); аутентификация и биллинг; выбор LLM-провайдера; ревью frontend и схем БД.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля рисков в ответе с `file`, `line` и дословным `evidence` из diff (QA-1) | Zero-shot P1-01: 0 из 14 замечаний с верной строкой (указаны `app/api.py:36-38` вместо 8–10). Замер: скрипт сверяет `evidence` с diff | ≥ 95 % | На каждом прогоне golden-набора (10 учебных diff) и еженедельно на выборке 20 реальных PR | Ответы API + [`tests_integration.md`](tests_integration.md) INT-03 |
| Доля запросов, где в prompt к LLM попал секрет (SEC-1) | Сейчас 100 % для diff с секретом: redaction отсутствует (`app/review_service.py:14`). Замер: подставной LLM сохраняет prompt, поиск по паттернам секретов | 0 % | Unit/integration на каждом CI + ежедневный аудит канареечных секретов | [`tests_unit.md`](tests_unit.md) U-01, U-02 |
| Доля ответов, прошедших JSON-схему OUT-1 | 0 %: сейчас возвращается `{"comment": str}` | 100 % | CI + мониторинг ошибок валидации ответа | [`tests_integration.md`](tests_integration.md) INT-01 |
| p95 времени ответа `POST /api/reviews` за скользящие 7 дней | Базы нет: timeout отсутствует (REL-1), сервис ещё не в проде. Ориентир до прода — прогон L-01 в [`tests_load.md`](tests_load.md) (подставной LLM 2–6 с, порог ≤ 8 с — это проверка накладных расходов сервиса, а не реального p95). Реальная база появится на первой неделе пилота, когда в вызовах будет настоящий провайдер | ≤ 12 с и 0 запросов > 12 с. Решение: если p95 > 12 с два дня подряд — возвращаемся к альтернативе C-QUEUE (очередь) в [`adr.md`](adr.md#рассмотренные-альтернативы) | Нагрузочный прогон до пилота, затем ежедневно | Поле `duration_ms` лога OBS-1 (`request_id`, длительность, статус) |
| Доля рисков, отмеченных ревьюером «полезно» (precision помощника) | Базы нет — появится за первую неделю пилота (5 ревьюеров). Замер: кнопка «полезно / не полезно» у каждого риска | ≥ 60 % за 2 недели пилота. Решение: < 40 % — останавливаем пилот и правим Context Pack; 40–60 % — продлеваем на 2 недели | Ежедневно в пилоте, итог — по окончании инкремента 3 ([`project_management.md`](project_management.md)) | Отдельная таблица `review_feedback` (`request_id`, номер риска, правило, оценка) — без текста diff и ответа, поэтому не нарушает OBS-1 |

## Почему изменение метрики подтвердит решение проблемы

- Первые три метрики — «гигиена»: без них помощник либо опасен (секреты), либо бесполезен (нельзя проверить риск). Их достижение проверяется автоматически в CI, поэтому регрессия будет видна сразу.
- p95 ≤ 12 с подтверждает, что REL-1 выполнен и зависший провайдер не блокирует ревью.
- Продуктовую ценность подтверждает только precision: если ревьюер принимает ≥ 60 % рисков, помощник экономит время, а не добавляет шум. Если precision ниже, проблема не решена даже при зелёном CI.

## Как использовали AI

- Для чего: найти расхождения между zero-shot ревью и правилами репозитория, сформулировать проблему через наблюдаемые нарушения; в Практике 2 (R.C.T.F., [`../practice_02/rctf/experiment.md`](../practice_02/rctf/experiment.md)) — проверить метрики на допущения и пороги решения.
- Тип промпта: zero-shot (P1-01) как baseline, master prompt (P1-02) для проверки, R.C.T.F. (E2-02) для метрик.
- Строка в [`prompts.md`](prompts.md): P1-01, P1-02; [`../practice_02/prompts.md`](../practice_02/prompts.md) E2-02.
- Что проверили и исправили сами: метрики «доля 5xx» и «успешный импорт `app.dependencies`» из прошлой версии заменили — первая описывала баг PR, а не проблему пользователя, вторая опиралась на непроверяемое утверждение о репозитории. Базовые значения посчитали по P1-01 и diff вручную. После R.C.T.F. добавили пороги решения для p95 и precision и вынесли отметки ревьюеров в отдельную таблицу — модель предлагала брать их «из опроса/отметок» и не заметила, что лог по OBS-1 их хранить не может.
