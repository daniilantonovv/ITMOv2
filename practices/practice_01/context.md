## Context Pack для первого рабочего сценария

Сценарий: ревьюер получает от помощника структурированный разбор одного PR (`POST /api/reviews`). Этот блок целиком встроен в Master Prompt v1 в [`prompts.md`](prompts.md).

### Факты и правила

Факты из diff (номера строк — в новой версии файла):

- `app/api.py:8–10` — добавлен `POST /api/reviews`, тело запроса — `payload: dict`, в сервис передаётся `payload["diff"]` без проверки.
- `app/review_service.py:13–16` — `review()` подставляет diff в prompt через f-string и возвращает `{"comment": answer}`.
- `app/api.py:3` — `review_service` импортируется из `app.dependencies`; содержимого этого модуля в diff нет.

Правила репозитория, которые влияют на этот PR. Источник — учебный кейс `CASE.md` из материалов курса (версия репозитория на коммите `86eba19`); ниже приведён их дословный текст, чтобы артефакты не зависели от наличия файла:

- `SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
- `API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.
- `REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
- `OUT-1`: ответ содержит `summary`, массив `risks` и массив `checks`; в `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.
- `SCOPE-1`: сервис только советует; он не пишет код и не выполняет действия в GitHub.
- `QA-1`: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
- `OBS-1`: в лог пишутся только `request_id`, длительность и статус; содержимое diff и ответа модели не логируется.

Намеренно **не** включены: правило `snake_case` для таблиц БД и правило i18n для frontend-строк — в PR нет ни БД, ни frontend.

### Формат входа и результата

- Вход: `POST /api/reviews`, JSON `{"diff": "<unified diff>"}`, `diff` — строка ≤ 20 000 символов.
- Результат (OUT-1):

  ```json
  {
    "summary": "string",
    "risks": [{"file": "app/api.py", "line": 10, "evidence": "строка из diff", "risk": "что сломается, какое правило"}],
    "checks": ["вход → ожидаемый результат"]
  }
  ```

- Ошибки, заданные правилами: 413 — diff > 20 000 символов (API-1); контролируемый ответ, если LLM не ответил за 10 с или вернул ошибку (REL-1).
- Ошибки, выбранные нами (проектное решение [`adr.md`](adr.md), не правило репозитория): 422 — нет поля `diff` или не строка (стандартное поведение Pydantic-схемы в FastAPI); 504 — timeout LLM, 503 — ошибка провайдера; тело ошибки без текста diff (вывод из OBS-1 и SEC-1).
- Тип `diff: str` в `app/review_service.py:13` — только аннотация: `app/api.py:9` принимает `payload: dict`, поэтому тип сейчас не проверяется.

### Ограничения и запрещённые действия

- Помощник не делает approve/merge/request changes и не пишет код (SCOPE-1).
- Не добавлять риск без цитаты строки diff или ссылки на правило (QA-1).
- Не отправлять в LLM секреты (SEC-1) и не логировать diff и ответ модели (OBS-1).
- Не утверждать то, чего нет в diff: например, «файла `app/dependencies.py` нет» — это неизвестно, а не факт.

### Хороший пример

```text
app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов,
что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться,
что в prompt осталось [REDACTED].
```

Номер строки взят из примера в `CASE.md`; при нумерации по содержимому hunk это строки 14–15 (заголовок hunk `+1,23` не совпадает с фактическими 16 строками). В наших артефактах используется нумерация по содержимому.

### Плохой пример

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

Нет файла и строки, нет правила, нет проверки — ревьюер не может ни подтвердить, ни опровергнуть.

### Что пока неизвестно

- Как создаётся `review_service` в `app.dependencies` и какой LLM-клиент за ним стоит (sync/async, есть ли встроенный timeout).
- Какой формат секретов нужно редактировать (только шаблоны токенов/ключей или ещё и `.env`-подобные строки) — нужен список паттернов от команды безопасности.
- Кто вызывает эндпоинт: ревьюер вручную, CI или GitHub App — влияет на аутентификацию (вне скоупа первого сценария).

## Как использовали AI

- Для чего: сравнить zero-shot ответ с правилами и понять, какого контекста модели не хватило; результат — этот Context Pack.
- Тип промпта: zero-shot (P1-01), затем master prompt (P1-02); Chain of Verification для фактов (Практика 2, E2-03).
- Строка в [`prompts.md`](prompts.md): P1-01, P1-02; [`../practice_02/prompts.md`](../practice_02/prompts.md) E2-03.
- Что проверили и исправили сами: Chain of Verification подтвердил 16 из 18 утверждений ([`../practice_02/chain_of_verification/experiment.md`](../practice_02/chain_of_verification/experiment.md)); два (422 и 504/503) не следуют из diff и правил — не удалили их, как предлагала модель, а явно пометили как наше решение из ADR. Пересчитали номера строк по hunk-ам diff (zero-shot указал `app/api.py:36-38`, реальные строки 8–10); убрали из прошлой версии ложный факт «`app/dependencies.py` не найден в репо» — в учебном репозитории нет кода приложения, поэтому это нельзя утверждать; отбросили нерелевантные правила (snake_case, i18n).
