# Tree of Thoughts

- Решение, для которого нужны альтернативы: как реализовать SEC-1 (удаление секретов из diff до внешнего LLM) — под-решение [`practice_01/adr.md`](../../practice_01/adr.md).
- Критерии выбора: K1 — гарантия, что секрет не уйдёт во внешний LLM (вес 0.4); K2 — польза ревью, не удалять лишнего (0.25); K3 — срок внедрения в инкременте 1, 5 дней (0.2); K4 — проверяемость unit-тестами без сети (0.15).

Инструмент: OpenCode 1.18.29, `vsellm/openai/gpt-5`, agent `plan`, вложение `adr.md`.

## Запрос

```text
Tree of Thoughts для архитектурного решения из adr.md: как реализовать правило SEC-1 («перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи»).
Критерии (вес): K1 гарантия, что секрет не уйдёт во внешний LLM (0.4); K2 сохранение пользы ревью — не удалять лишнего (0.25); K3 сложность и срок внедрения в инкременте 1, 5 дней (0.2); K4 проверяемость unit-тестами без сети (0.15).
Сгенерируй ровно три принципиально разные альтернативы:
A — собственные regex-паттерны в модуле redaction;
B — готовый набор правил сканера секретов (например, правила gitleaks/detect-secrets), подключённый как библиотека;
C — не редактировать, а отклонять diff с найденным секретом (HTTP 422 с указанием строки), чтобы автор сам убрал секрет.
Для каждой: плюсы, минусы, оценка 1–5 по каждому критерию и взвешенная сумма. Затем отбрось самую слабую ветку с причиной, сравни две оставшиеся на худшем для каждой сценарии (секрет незнакомого формата; diff с 50 строками test-фикстур с фейковыми ключами) и выбери одну. Добавь, как проверить выбор тестом.
Формат: таблица альтернатив, «Отброшено:», «Худшие сценарии:», «Выбор:», «Проверка:». Без скрытых рассуждений — только описанные альтернативы и оценки.
```

## Внешне описанные альтернативы

Полный ответ — [`result.md`](result.md).

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A — свои regex-паттерны в `app/redaction.py` | Полный контроль, без зависимостей, детерминированно, легко тестировать офлайн | Неполное покрытие форматов, ручная поддержка | K1 3, K2 4, K3 5, K4 5 → **3.95** |
| B — правила сканера секретов (detect-secrets / gitleaks) как библиотека | Готовые правила, лучшая стартовая полнота, обновления | Интеграция и вес, шире ложные срабатывания | K1 4, K2 3, K3 3, K4 4 → **3.55** |
| C — отклонять diff с секретом (422) | Для известных форматов исключает утечку, простая логика | Блокирует diff с фикстурами, плохой UX, зависит от детектора | K1 4, K2 2, K3 4, K4 5 → **3.65** |

Отброшено моделью: B — наименьшая сумма и риск не уложиться в 5 дней.
Худшие сценарии: секрет незнакомого формата — утечка и у A, и у C; 50 строк фикстур с фейковыми ключами — A лишь редактирует лишнее, C блокирует весь запрос.

## Выбор

- Выбранная альтернатива: A.
- Почему: при одинаковом провале на незнакомом формате A сохраняет пользу ревью (K2) и укладывается в инкремент 1.
- Как проверим: корпус ≥ 30 канареечных секретов (U-01), идемпотентность (U-09), скорость < 50 мс на 20 000 символов (U-10), подставной LLM в INT-04 сохраняет prompt и падает при любом совпадении с корпусом.
