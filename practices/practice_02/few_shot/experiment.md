# Few-shot

- Артефакт Практики 1: [`product_management.md`](../../practice_01/product_management.md), раздел «User stories и acceptance criteria», фича «Защита секретов (US-2)».
- Что хотим улучшить: у US-2 был один сценарий (GitHub-токен в добавленной строке). Не покрыты другие форматы секретов, многострочные ключи, удалённые строки diff и ложные срабатывания — критерии приёмки SEC-1 были неполными.

Инструмент: OpenCode 1.18.29, `vsellm/openai/gpt-5`, agent `plan`, без вложений (всё в запросе).

## Примеры

### Хороший результат

```gherkin
Scenario: Негативный — diff содержит токен
  Given diff содержит строку "+GITHUB_TOKEN = 'ghp_TEST0000000000000000000000000000000'"
  When ревьюер отправляет POST /api/reviews с этим diff
  Then prompt, переданный в LLM, содержит "[REDACTED]"
  And prompt не содержит подстроку "ghp_TEST"
```

Почему хороший: конкретный вход, одно действие, результат проверяется автоматически, есть связь с правилом.

### Плохой результат

```gherkin
Scenario: Секреты защищены
  Given в коде могут быть секреты
  When пользователь делает ревью
  Then секреты не утекают и система работает безопасно
```

Почему плохой: нет конкретного входа, «безопасно» не наблюдаемо, тест написать нельзя.

## Запрос

```text
Задача: переписать acceptance criteria (Gherkin) для фичи "Защита секретов (US-2)" AI-помощника ревьюера PR. Правило SEC-1: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.

Пример ХОРОШЕГО сценария (так надо):
  Scenario: Негативный — diff содержит токен
    Given diff содержит строку "+GITHUB_TOKEN = 'ghp_TEST0000000000000000000000000000000'"
    When ревьюер отправляет POST /api/reviews с этим diff
    Then prompt, переданный в LLM, содержит "[REDACTED]"
    And prompt не содержит подстроку "ghp_TEST"
Почему хороший: конкретный вход, одно действие, наблюдаемый и проверяемый автоматически результат, ссылка на правило.

Пример ПЛОХОГО сценария (так нельзя):
  Scenario: Секреты защищены
    Given в коде могут быть секреты
    When пользователь делает ревью
    Then секреты не утекают и система работает безопасно
Почему плохой: нет конкретного входа, результат нельзя проверить тестом, "безопасно" — не наблюдаемо.

Сделай в стиле хорошего примера 4 сценария для US-2: (1) пароль в строке подключения к БД в URL, (2) приватный ключ PEM из нескольких строк, (3) ложное срабатывание — обычный код со словом token не должен меняться, (4) секрет в удалённой строке diff (начинается с "-"). Только Gherkin, без пояснений.
```

## Что получили

Модель вернула 4 сценария строго в формате хорошего примера (полный ответ — [`result.md`](result.md)):

1. Пароль в `DATABASE_URL` (`postgres://user:passw0rd@...`) → в prompt есть `[REDACTED]`, нет `passw0rd`.
2. Многострочный PEM-ключ → в prompt есть `[REDACTED]`, нет `BEGIN PRIVATE KEY`.
3. Ложное срабатывание: `+print('access token expired')` не изменяется, `[REDACTED]` нет.
4. Секрет в удалённой строке `-PASSWORD = 'SuperSecret123!'` → в prompt его нет.

Разница с zero-shot: без примеров в P1-01 модель писала «add tests for error cases» — без входа и ожидаемого результата. С двумя примерами все 4 сценария сразу получились проверяемыми.

## Что изменили в исходном артефакте

- Файл и раздел: [`practice_01/product_management.md`](../../practice_01/product_management.md) → «User stories и acceptance criteria» → `Feature: Защита секретов (US-2)`.
- Изменение: к одному сценарию добавлены 4 новых (пароль в URL, PEM-ключ, удалённая строка, ложное срабатывание). Всего сценариев в файле стало 11.
- Как проверили: каждый сценарий сверили с SEC-1 из [`CASE.md`](../../practice_01/CASE.md); убедились, что у каждого есть конкретный вход и утверждение о подстроке, которое можно проверить через `FakeLLM.last_prompt` (INT-04 в [`tests_integration.md`](../../practice_01/tests_integration.md)).
- Что отклонили: утверждение «prompt не содержит `BEGIN PRIVATE KEY`». Заголовок PEM — не секрет, и ревьюеру полезно видеть, что в PR добавили ключ. Заменили на проверку тела ключа (`MIIEvQIBADAN`). В сценарии с удалённой строкой убрали требование `[REDACTED]`: оставили только проверку, что секрета нет, — способ маскировки удалённых строк ещё не выбран.

## Контрольный запуск без техники

Чтобы отделить эффект примеров от эффекта самой задачи, тот же запрос выполнен без блоков «Хороший результат» и «Плохой результат» — [`result_control.md`](result_control.md). Сравнение с P1-01 контролем не считается: там другая задача («найди проблемы в PR»). Из-за недоступности шлюза VseLLM контроль выполнен на Claude Opus 5, а не на `gpt-5`, и исполнитель уже видел основной ответ — ограничение указано в файле.

Разница между ответом с примерами и без них:

| Признак | Без примеров (контроль) | С двумя примерами (E2-01) |
|---|---|---|
| Вход сценария | Описан словами: «строка подключения с паролем» | Конкретная строка: `+DATABASE_URL = 'postgres://user:passw0rd@db.internal:5432/appdb'` |
| Проверяемый результат | «пароль заменён на маркер редактирования», «не передаётся во внешний сервис» — маркер не назван, проверку писать не по чему | `prompt содержит "[REDACTED]"` и `prompt не содержит "passw0rd"` — прямо переносится в assert |
| Наблюдаемый объект | «сервис готовит запрос» — не сказано, что именно смотреть | `prompt, переданный в LLM` — совпадает с `FakeLLM.last_prompt` в INT-04 |
| Пригодность как AC | Нужна доработка человеком: выбрать маркер, выбрать точку наблюдения | Готово к автоматизации без правок |

Вывод: примеры влияют не на структуру (Gherkin получился в обоих случаях), а на конкретность входа и наблюдаемость результата. Это ровно то, чего не хватало исходным критериям US-2.
