# R.C.T.F.

Выбранный слабый артефакт Практики 1 — [`practice_01/problem.md`](../../practice_01/problem.md): у двух метрик базовое значение было допущением, у всех — нет порога принятия решения.

- **Role:** продуктовый аналитик внутренних инструментов разработки; формулирует метрики, которые можно посчитать по логам и тестам.
- **Context:** `problem.md` (таблица метрик), `CASE.md` (правила SEC-1…OBS-1); лог по OBS-1 содержит только `request_id`, длительность и статус; пилот — 5 ревьюеров, 2 недели.
- **Task:** найти метрики, у которых (а) база — допущение, (б) источник не позволяет посчитать метрику при OBS-1, (в) нет порога решения; предложить исправление; не больше одной новой метрики.
- **Format:** таблица «Метрика | Проблема | Исправленная формулировка | Как посчитать | Порог решения» + строка «Не менять:».

Инструмент: OpenCode 1.18.29, `vsellm/openai/gpt-5`, agent `plan`, вложения: `rctf.txt` (запрос ниже), `problem.md`, `CASE.md`.

## Полный запрос

```text
Role: ты — продуктовый аналитик внутренних инструментов разработки, умеешь формулировать метрики, которые можно посчитать из логов и тестов.
Context: приложены problem.md (проблема и таблица метрик AI-помощника ревьюера PR) и CASE.md (правила SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1). Лог сервиса по OBS-1 содержит только request_id, длительность и статус. Пилот: 5 ревьюеров, 2 недели.
Task: найди в таблице «Метрики» problem.md метрики, у которых (а) базовое значение — допущение или «нет данных», (б) источник данных не позволяет посчитать метрику при ограничении OBS-1, (в) нет порога принятия решения. Для каждой предложи исправленную формулировку. Не добавляй больше одной новой метрики.
Format: markdown-таблица с колонками: Метрика | Проблема (а/б/в) | Исправленная формулировка | Как посчитать (конкретный источник) | Порог решения. После таблицы — одна строка «Не менять:» со списком метрик, которые уже корректны.
```

## Что получили

Полный ответ — [`result.md`](result.md). Кратко:

| Метрика | Проблема по модели | Что предложила модель |
|---|---|---|
| p95 времени ответа | (а) база — допущение | Считать по `duration` лога OBS-1 за 7 дней, отдельно — прогон `tests_load.md`; порог p95 ≤ 12 с, 0 запросов > 12 с |
| Precision (доля принятых рисков) | (а) база — «нет данных» | Доля рисков с отметкой «полезно» за 2 недели пилота; порог ≥ 60 % |

«Не менять»: QA-1-метрика, доля секретов в prompt, доля ответов по схеме OUT-1. Новых метрик модель не добавила.

Формат R.C.T.F. дал ровно то, что просили: таблицу без лишнего текста, по правилам из вложений. Из трёх запрошенных проблем модель разметила только (а) «база — допущение»: (б) «источник несовместим с OBS-1» не применён (отметки ревьюеров нельзя хранить в логе, где по OBS-1 есть только `request_id`, длительность и статус), (в) «нет порога решения» не отмечен ни у одной метрики, хотя порогов не было ни у одной — пороги модель добавила молча, в отдельной колонке.

## Что изменили в исходном артефакте

- Файл и раздел: [`practice_01/problem.md`](../../practice_01/problem.md) → «Метрики», строки «p95 времени ответа» и «Доля рисков, отмеченных ревьюером „полезно“».
- Изменение: p95 — окно 7 дней, первая база из L-01, порог решения «p95 > 12 с два дня подряд → альтернатива C из ADR». Precision — пороги решения (< 40 % стоп, 40–60 % продление) и источник `review_feedback` (`request_id`, номер риска, правило, оценка) вместо «опроса».
- Как проверили: каждый источник данных сверили с OBS-1 — ни одна метрика не требует хранить текст diff или ответа; пороги согласуются с [`project_management.md`](../../practice_01/project_management.md) (инкремент 3).
- Что отклонили: источник «выгрузка из опроса/отметок ревьюеров» — неоднозначен и при хранении в логе нарушил бы OBS-1. Идею «окно 7 дней» приняли. Список «Не менять» приняли частично: у трёх метрик из него цель одновременно является порогом решения (0 % секретов, 100 % схемы OUT-1, ≥ 95 % рисков с evidence — любое отклонение блокирует релиз в CI), поэтому отдельная колонка порога им не нужна; это отмечено прямо в таблице метрик.

## Контрольный запуск без техники

Тот же артефакт и тот же предмет, но без Role, Context, Task и Format: `Посмотри таблицу «Метрики» в приложенном problem.md и скажи, какие метрики слабые и что с ними не так.` Ответ — [`result_control.md`](result_control.md). Из-за недоступности шлюза VseLLM выполнен на Claude Opus 5, а не на `gpt-5`; ограничение указано в файле.

| Признак | Без R.C.T.F. (контроль) | С R.C.T.F. (E2-02) |
|---|---|---|
| Форма ответа | Четыре абзаца прозы, метрики перечислены в произвольном порядке | Таблица «Метрика → проблема → исправленная формулировка → источник → порог», сразу переносится в `problem.md` |
| Что именно исправить | Не сказано: «порог взят с потолка», «вызывает вопросы» | Готовая формулировка и конкретный источник данных для каждой метрики |
| Ограничения из контекста | OBS-1 и условия пилота не учитываются — контроль их не знал | Источники подобраны под ограничение лога OBS-1 |
| Побочный эффект | Предложил убрать две метрики (SEC-1 и OUT-1) как «дублирующие тест» и добавить новую — «сэкономленное время ревьюера», которую нечем измерять | Явный запрет «не больше одной новой метрики» удержал ответ в рамках |

Полезное в контроле тоже было: замечание, что 12 секунд ожидания — много для инструмента внутри ревью. Записали в [`analysis.md`](../../practice_01/analysis.md) как повод вернуться к альтернативе C-QUEUE, если пилот покажет, что ревьюеры не ждут ответ.

Вывод: R.C.T.F. влияет не на то, найдёт ли модель слабые места (нашла в обоих случаях), а на то, можно ли применить ответ без переписывания: Format даёт готовую структуру, Context не даёт предлагать источники, несовместимые с OBS-1.
